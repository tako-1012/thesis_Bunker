# 指示書022：Gazebo の LiDAR で地図を作り直しながら走った結果（10 か所、Claude が通常の Docker で実行）

Codex の実装（`codex/022-gazebo-lidar`）は Gazebo を走らせていない。Claude が `thesis/jazzy-gz:1` の Docker で 3 か所、次に 10 か所の順で走らせた。
古い地図のまま走る場合と、半径 10m が誤差なく見える場合は、021 の保存済みの実測（`results/gazebo_online/physical_run/`）をそのまま並べている（走らせ直していない）。
数値はすべて `runs.csv`・`summary.csv`・`gazebo_lidar_log.txt`（`experiments/gz_lidar_report.py` の出力）から。手で作った数値はない。

## 結果（10 か所、同じ world・同じ地点・同じスタート）

| 方法 | 完走 | 立ち往生 | 転倒 | 経路なし（no_path） |
|---|---|---|---|---|
| 古い地図のまま（021） | 0/10 | 9 | 1 | 0 |
| 半径 10m が誤差なく見える（021） | 9/10 | 0 | 1 | 0 |
| **LiDAR（今回）** | **4/10** | 0 | 2 | 4 |

- LiDAR で完走：`08OB86_00294`、`08OB86_-0205`、`08OB87_-0706`、`08OB88_00332`（4 か所とも半径 10m の場合も完走）。
- 経路なし：`08OB88_-1417`、`08OB88_-0167`、`08OB89_-0347`、`08OB89_-0847`。センサーの途切れではなく（センサーの誤りは 0 件）、計画が「通れる経路がない」を返した。
- 転倒：`08OB88_01832`（x≈199.6m）と `08OB89_00152`（y≈199.6m）。どちらも**地図の端（200m）**で起きた。`08OB89_00152` は 021 でも両方の方法で転倒した場所で、地点が端から 0.25m・0.75m にある境界の問題。`08OB88_01832` も地点の 1 つ（マス (397,169)、x=198.5m）が端から 1.5m にあり、その近くの端（x≈199.6m、地図の外に出たサンプル 20）で転倒した。同じ種類の問題と考えられる（地点はずらしていない）。
- 点群から作った高さと本当の高さの差（見えたマス）：中央値は各砂浜で 0.7〜1.5cm、95% 値は 4〜72cm（漂着物の上面を地面として測ったマスを含む）。
- 地図の更新（点群のデコード・座標変換・統合・コストの再計算）：1 回あたり中央値 0.08〜0.10 秒、最大 0.76 秒。1 回の計画：中央値 0.04〜0.10 秒。
- 漂着物のマスに触れた数：LiDAR の 10 走行すべてで 0。

## 経路なしの原因（Claude が記録を調べた結果）

点群の地図は、本当の地図より通れないマスが多い（見えたマスで、点群の地図 1064・1824・11593・7273 に対し、本当の地図 691・912・10378・5892）。その結果、狭い通路が閉じて経路なしになった。
漂着物として検出されたマス（点群の地図）を、本当の漂着物のマスと Gazebo の箱の位置と比べた：

| 砂浜 | 検出 | 本当の漂着物 | 箱の外で、箱に 4 方向で隣り合うマス | それより遠いマス | 水・データなし（もともと通れない） |
|---|---|---|---|---|---|
| 08OB88_-1417 | 333 | 84 | 180 | 60 | 0 |
| 08OB89_-0347 | 779 | 179 | 403 | 186 | 0 |
| 08OB89_-0847 | 6308 | 155 | 454 | 253 | 5442 |
| 08OB88_-0167 | 1230 | 211 | 567 | 322 | 124 |

- **誤検出のおよそ 7 割は、漂着物の箱のすぐ隣の 1 マス**。Gazebo の箱の側面はマスの境目にあり（`data_prep/export_gazebo.py`）、箱は漂着物より 0.5m 高い。
  側面に当たった点は、測距の雑音（0.02m）でちょうど隣のマスにも入る。そこは古い地図より 0.3m 以上高いので漂着物とされる。
  計画では漂着物をさらにロボットの大きさ（0.5m＝1 マス）だけ膨らませるので、漂着物のまわりが実際より 1 マス広く通れなくなる。
- 残りは、漂着物から 1〜2 マスの場所（中央値の距離 0.5m）で、傾斜は周りとほぼ同じ（3〜5°）。急斜面の誤りではない。
- 「判定の高さ 0.3m・3 点」「古い地図を基準にする」は事前に決めた仮定で、test の結果を見て変えていない。結果を良くするための調整もしていない。

## 走らせ方と、そのために変えたこと

```bash
THESIS_REAL_TIME_FACTOR=0.3 THESIS_STALE_TIMEOUT_S=1.0 \
  bash ros2_jazzy/gz_checks/run_lidar_checks.sh <出力先> --patch-count 10
python3 experiments/gz_lidar_report.py <出力先>
```

- **地形の見た目を三角形のメッシュにした**（`gz_checks/terrain_mesh.py`）。GPU LiDAR（ogre2）は見た目だけを測るが、Gazebo の heightmap の見た目のシェーダーは GPU なしでコンパイルできず落ちた。
  物理（衝突）は今までどおり heightmap。メッシュと heightmap の一致は、点の高さと地図の中央値の差が中央値 −1mm、94% が ±10cm 以内で確かめた。
- **シミュレーションを実時間の 0.3 倍にした**（`THESIS_REAL_TIME_FACTOR`）。CPU で描画すると点群が遅れ、0.5 秒の途切れの基準で止まった（3 か所の試走で 3/3 と 2/3 が `lidar_unavailable_or_stale`）。
- **途切れの基準を 1.0 秒にした**（`THESIS_STALE_TIMEOUT_S`、既定は 0.5 秒のまま）。0.3 倍・0.5 秒でもまだ 2/3 が止まったため。10 か所の本番では途切れによる停止は 0 件。
  計画の時間は実時間（壁時計）で測っているので、シミュレーションが遅いぶん、実機より楽観的な見積もりになっている。
- 3 か所の試走（落ちた回・止まった回）は、設定を変える前の記録なのでリポジトリに入れていない。

## 注意（論文・修論に書くときに必要なこと）

- LiDAR の仕様（VLP-16 相当、16 本・±15°・10Hz・30m・雑音 0.02m）、取り付けの高さ 0.8m、漂着物の判定（0.3m・3 点）はすべて仮定。
- 半径 10m（誤差なし）と LiDAR（30m・疎な走査線・陰・雑音）は、範囲も見え方も違う。陰だけの効果を比べたものではない。
- 漂着物は、Gazebo では「漂着物のマスを覆う箱（0.5m 高い）」として置いている。誤検出の多くは、この箱の側面がマスの境目にあることによる。
  実際の漂着物でも、物の側面の点が隣のマスに入ることは起きうるので、「点群の地図は障害物を太らせやすく、狭い通路を閉じやすい」という結果として扱う。
- 10 か所なので検定はしていない。エネルギーは集計していない。
