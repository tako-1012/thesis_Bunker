# 051 計画に使った地図の保存と接近・経路なしの調査

実装・容量試算コミットは `245e3a6ccaff7556194e60fcf49633cd15f19ccf`。同じ経路の再送の照合は `fcf931066b92088bc891ccc62b0267e21018b27f`。基点は `realtime-map` の `cb6bdf406d5ec36b56f918e900d6f401ee25c584`。ブランチは `codex/051-plan-map-snapshots`。この報告は後続コミットに収録する。 [実装と容量試算](https://github.com/tako-1012/thesis_Bunker/commit/245e3a6ccaff7556194e60fcf49633cd15f19ccf)

`--save-plan-maps` は初回のオンライン探索と、その後の再探索で使った地図を保存する。044の最多255探索では、保存済みの地図を使った追加容量の試算は約26.6 MB、測定した最大サイズで積み上げると約32.4 MBだった。既存の044の60走行は、調査に必要な地図が未保存であることを表示してスキップした。 [容量試算の出力](size_log.txt)

## 実装と変更ファイル

- `conference/ros2_jazzy/gz_checks/endpoint_runtime.py` と `safety_runtime.py` を変更。探索直前の通行不可と探索コスト、観測済み・計画上既知のマスク、検出障害物・事前障害物・急斜面と各膨張、姿勢、探索要求のシミュレーション時刻、経路を記録する。 `prior_veto` では `veto_supported` も含む。端点緩和を使うときは実際の探索に使った緩和後の地図を記録する。受け渡しに成功した経路と終端失敗には探索番号を関連付ける。
- `conference/ros2_jazzy/gz_checks/plan_maps.py` を追加。マスクはビット詰め、探索コストは直前の保存値とのXORをバイト平面に並べて圧縮する。元のfloat64のビットを復元できる。実行時に追加記録の合計が100,000,000バイトを超えそうな場合は、記録を止めて欠測の開始時刻を残す。経路計画・走行は継続する。 `plan_maps/` の `plan_*.npz` は探索順に復元する。
- `conference/ros2_jazzy/gz_checks/lidar_checks.py`・`lidar_planner.py`・`run_lidar_checks.sh` を変更。走行ラッパーとROSパラメータに新しい指定を通し、有効化した走行のmanifestに記録する。箱の正解位置は `debris_footprints.csv` に保存し、走行後の集計で使う。
- `conference/experiments/plan_map_inspect.py` を追加。箱への最接近は、軌跡を標本間で線形補間して得た中心と箱の最小距離で求める。追従側の経路版記録があるときはその時刻に使っていた経路と受け渡し記録を照合する。経路版記録がない場合は計画側の手渡し時刻を使い、根拠を出力する。 `approach.csv` は検索経路・受け渡し経路の箱への距離、箱に重なる検出セル、箱の周囲の障害物膨張と経路の交差を出す。 `goal_cell.csv` は終端の失敗と、その目標が最初に塞がった保存地図の理由・時刻を出す。 `skipped.csv` に欠測理由を出す。
- `conference/tests/test_plan_map_snapshots.py` を追加。基点の実装を同一環境で実行し、既定のmanifest・mission・コマンド・計画CSV・診断NPZがバイト単位で一致することを比較した。追加記録からコストと経路を復元し、模擬実行で探索・受け渡し・終端失敗を照合した。基点のGitオブジェクトが必要。
- `conference/results/plan_map_snapshots/` に `estimate.py`・`size_log.txt` とこの報告を追加。

## 容量の見積もり

044の60走行の探索数は31〜255、中央値106。030のコミット済み400×400診断地図35枚を25走行に分け、初回全量25件と後続の差分10件を実際に圧縮した。同じ走行の保存経路を使い、経路が残っていない地図では保存姿勢の1点をサイズ計算に使った。 `veto_supported` には観測済みマスクと同じ大きさのビット列を含めた。容量は10進MB。 [044の走行別探索数](../eval_044/common_eval/runs.csv)

| 探索回数 | 測定サイズ中央値で積算 | 測定サイズ最大で積算 |
|---:|---:|---:|
| 31 | 3.962 MB | 4.730 MB |
| 106 | 11.540 MB | 13.991 MB |
| 255 | 26.594 MB | 32.390 MB |

これは追加する `plan_maps/` の見積もりで、通常の軌跡や診断地図などの容量は別にかかる。保存できる探索数は地図の変化量で異なるため、100 MBの制限を実行時にも設けた。上限以降は `incomplete.json` を見て、集計側が根拠のない経路を選ばない。研究PCでは生データを残し、報告には容量とパス・SHA-256を記録する。 [研究PCの保存ルール](../../RESEARCH_PC_ja.md)

## 確認範囲

Gazeboや研究PCでの実験は未実施。044の接近2件を再診断する地図は未収録。起動時に渡す準備済み巡回経路には対応するオンライン探索がないため、最初のオンライン受け渡し以前に最接近した場合は地図での調査を保留する。記録が対応するのは探索要求の地図であり、手渡し時に再検証した地図は含めていない。探索と後続の手渡しは時刻も経路も別々に保存する。

箱付近の膨張マスは地理的に切り出すため、近くの別の検出物に由来する可能性がある。経路との交差を調べられるが、別の膨張規則で計画していた場合の経路や物理接触までは判定できない。前の観測の通行不可が計画側に保持されていたマスは `retained_planner_observation` と表示する。最初に塞がった時刻は保存した探索の時刻で、探索の間に起きた変化の時刻は特定できない。書き込み時間と走行の実時間倍率への影響は未計測。
