# Gazebo での実行結果（Claude が通常の Docker で実行）

Codex の環境では Gazebo を動かせなかったため、Claude が `run_online_batch_checks.sh`（イメージ `thesis/jazzy-gz:1`、Gazebo 8.11.0）で 20 走行を実行した。
実行前に、Gazebo 用の地図の書き出しの不具合（`scenario_to_mapfile` の引数不足）を直した（コミット `bcf199c`）。結果の全文は `gazebo_online_log.txt`・`runs.csv`・`summary.csv`、元の記録は `raw/`。

## 結果（点群の砂浜の test 10 か所、漂着物あり、事前の地図は漂着物なし、急斜面の膨らませ 0.5m の TA*-S）
| | 完走 | 立ち往生 | 転倒 | 回れた地点（中央値） |
|---|---|---|---|---|
| 古い地図のまま走る（fixed） | **0/10** | 9/10 | 1/10 | 0.5/5 |
| 走りながら計画し直す（online、半径 10m） | **9/10** | 0/10 | 1/10 | 5/5 |

- 古い地図のまま走ると、9 か所で漂着物にぶつかって止まった（開始から 20〜250 秒）。中心の軌跡は漂着物のマスに入っていない（`debris_cells` は 0〜2）が、
  止まった位置は漂着物のマスから約 0.8m で、車体の前端（中心から 0.51m）が漂着物の箱に当たって止まったと考えられる（Claude が 3 か所で確かめた）。
  **通れない場所への接触の数は中心の軌跡だけで数えているので、車体の接触を少なく数える。**
- 1 回の計画の時間（online、走行ごとの中央値の中央値）は約 0.08 秒、最大は 1.15 秒。

## 注意（結果の読み方）
1. **`08OB89_00152` の転倒（両方の方法）は、シミュレーションの境界によるもの。**
   - 5 地点のうち 2 つが地図の端から 0.25m と 0.75m の所にあった（地点の選び方が地図の端を考えていない）。
   - そこへ向かった BUNKER が、地図の端（y=199.75m）のすぐ手前（y≈199.5m、傾斜 7〜10°）で、車体が地形の外にはみ出して転倒した。
   - 実際の砂浜は地図の外にも続くので、手法の良し悪しとは関係ない。この 1 か所は、比較から外すか、注記して示すこと。
2. `08OB88_-0167`（019 で転倒した砂丘の入り組んだ所）では、計画し直す方法でも急斜面のマスに 27 マス触れた（経路からのずれ）。転倒はせず完走した（最大の横傾き 43°、縦傾き 52°）。
3. **計画の時間は実際の時間（壁時計）、ロボットはシミュレーションの時間で動く。** この環境では Gazebo が現実の約 1/1.3〜1/4 の速さでしか進まなかった
   （4097 画素の地形、GPU なし）。計画している間にロボットが進む距離は、本来より短く見える（計画が間に合うかについて有利な方向）。
   計画の時間そのもの（最大 1.15 秒）は 1m/s の走行に比べて十分短いが、この点は書き添えること。
4. 10 か所なので検定はしていない。両方完走した組がないため、対にした差は出ていない（`paired_differences.csv` は空）。
