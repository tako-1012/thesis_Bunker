# 008 の記録の見直し：順番を最適化する効果は大きい（Claude、2026-11-26）

## きっかけ
- 11/26 に利用者と、修論の範囲を「ドローンが撮ったばかりの地図（正とみなす）の上で、人が選んだ地点を効率よく回る」と決めた。
- 008 は「順番の工夫は効果が小さい（負の結果）」とされていた。しかし 008 で比べたのは、**直線距離で解いた最適な順**と**地形で解いた最適な順**で、どちらも最適化した順どうしだった。
- 実際のシステムで比べるべき相手（選んだ順のまま回る・近い所から回る）は、比べていなかった。

## やったこと（あとから足した確かめ。008 の指示書では前もって決めていない）
- 008 の保存した行列 `multi_goal_tour/pair_costs.csv`（地形と登りを考えた、向きのあるコスト。区間は平滑化済み）と、最適な順 `tours.csv`（`terrain dir`、Held–Karp の厳密解）をそのまま使った。
- 次の 2 つの順のコストを、同じ行列で足し上げた。
  - **選んだ順のまま**：008 で地点を引いた順（0→1→…→n→0）。人が選んだ順の代わりで、ランダムなので人の順より悪い側に寄る。
  - **近い順**：直線距離で、いちばん近い未訪問の地点へ行く。
- 確かめ：行列から足し上げた最適な順のコストは、008 の記録の `cost_dir` と 300 件すべてで一致した（相対差の最大 2e-16）。
- スクリプトは `recompute.py`、出力は `recompute_log.txt`・`baselines.csv`。

## 読み方
- **順番を最適化する効果は大きい**。地点が多いほど大きい。近い順と比べても、12 地点では中央値で 13.5% 減る。
- **地形をコストに入れる効果**（直線距離で解いた最適な順と比べて）は、008 の作った地形では小さかった。
  地形で大きく遠回りになる所（急な段差・砂丘・水路など）が少ない地形だった可能性がある。本物の砂浜の地図では確かめていない。
- **限界**：
  - 地点はランダムに選んでいて、ゴミの集まり方（固まって出る）とは違う。
  - 「選んだ順」はランダムで、人が実際に選ぶ順ではない。
  - コストはエネルギーの目安（登りを含む）で、時間ではない。
  - どれもシミュレーションの地形の上の、走る前の計画の値（実際に走った値ではない）。
