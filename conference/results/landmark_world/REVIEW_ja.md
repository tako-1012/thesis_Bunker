2. **全テスト**：076 と合わせた状態で、Claude の環境で全テストを走らせた（076 の REVIEW の「全テストの結果」）。
3. **既定の出力**：新しいテストが、直す前の実装と同じ環境で、出力の木・起動・分岐をバイト単位で比べている。`lidar_checks.py` の分岐を読み、目印なしのとき、古い地図を変える条件（`prior_variant`）の流れとエラーの文が今までと同じであることを確かめた。
4. **中心の差分を読んだ**：
   - 目印は古い地図（prior）と評価の正解（truth）の両方の「岩」に入るので、評価の漂着物（正解の岩 − 古い地図の岩）には入らない。箱までの距離の基になる `debris_footprints.csv` は、目印を足す前の世界から書いている。
   - Gazebo の世界の地形（`truth.npz` から作るメッシュ）は目印なしで、目印は別のモデル（衝突と見た目の両方）として足している。
   - **「ドローンの地図」の点群と Gazebo の目印の向き**：点群は `R(yaw)`（反時計回り）で回し、Gazebo の姿勢の yaw も反時計回り。箱の幅・奥行きの軸、地形の頂点の座標（i × 0.5m）も両方で同じ。
   - 目印を置くと、古い地図で初めの経路を引き直す。引けないときは止める（`0167` の 160 個・シード 0 で 5 区間目が引けない。報告どおり）。
5. **わざと壊す**：点群の目印の回転の向きを逆にする → テスト 4（点が目印の表面にあるか）が検出した。
6. **数字の出し直し**：Gazebo を走らせていないので、走行の数字はない。点群の大きさ（目印 0 個で 19.86MB、160 個で 20.84MB）は、研究 PC で記録するときに確かめる。
