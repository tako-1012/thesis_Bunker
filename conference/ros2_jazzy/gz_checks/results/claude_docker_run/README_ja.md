# Gazebo での確認の結果（Claude が Docker で実行）

Codex の環境では Docker の容量が足りず、Gazebo での確認ができませんでした（`../environment.json`）。
そこで Claude が、クラウドの環境の Docker（`osrf/ros:jazzy-desktop-full`、Gazebo 8.11.0）で
`run_gz_checks.sh` を実行しました。結果の全文は `results.json` にあります。

## 実行の前に直したこと（コミット `29d4167`）
最初の実行では、Gazebo のロボットと球の位置が ROS2 に届かず、`missing physical telemetry` で止まりました。
Gazebo Harmonic の `PosePublisher` は `<topic>` の指定を無視して、`/model/<モデル名>/pose` で位置を出すためです。
ブリッジの設定（`bridge.yaml`）と `checks.py` を、この名前に合わせて直しました。
`tests/test_ros2_gz.py` には、名前が合っていることを確かめる検査を加えました。

## 結果
| 項目 | `flat_test` | 本物の砂浜 `real_08OB87_-0206` |
|---|---|---|
| 球を落とした高さと地図の差の最大（20 か所） | 0.000001m | 0.0066m |
| BUNKER を置いて 5 秒（落下・ずれ） | なし | なし |
| 巡回 5 点の完走 | 完走（249 秒） | 完走（348 秒） |

| 通れない場所に触れたマス | 0 | 0 |
| roll の 95% 値（Gazebo ／ 地図から計算） | 0.0° ／ 0.0° | 4.8° ／ 4.5° |
| pitch の 95% 値（Gazebo ／ 地図から計算） | 0.0° ／ 0.0° | 6.2° ／ 6.3° |

前進・旋回（`flat_test`）：前進は指令の 99.7%（10 秒で 4.99m）、その場旋回は指令の 89.3%（10 秒で 4.46rad）。
旋回が少し足りないのは、車輪の横向きの摩擦（仮定値 `mu2 = 0.1`）で滑るためと考えられます。

## 気づいたこと：本物の砂浜のデータは 0.1m 刻みの段々になっている
本物の砂浜の傾きの記録（`report_real_08OB87_-0206/attitude.png`）では、roll と pitch がちょうど 0 になる区間が長く続き、ところどころで跳ねます。
調べると、模型や記録の誤りではなく、**標高データが 0.1m 刻みの段々になっている**ためでした。
`08OB87_-0206` では、陸のマスの 50% がちょうど 0.1m の倍数の高さで、となりのマスと同じ高さの組が 31% ありました。
段の上は傾き 0、段の境（0.5m で 0.1m）は約 11° の傾きになります。Gazebo はこの段々をそのまま再現しています。
このことは、指示書009の本物の砂浜の結果（傾き・凸凹の値）にも関係するので、今後の扱いを決める必要があります（未対応）。
