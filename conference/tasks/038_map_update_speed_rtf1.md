## 背景（別の環境の会話は共有されないので、ここに書く）
- Gazebo の走行は、ずっと**実時間の 0.3 倍**で行っている。研究 PC の確認（`results/rtf_check/`、2026-11-07）で次のことが分かっている。
  - Gazebo そのものは 1 倍で動く（実測倍率 0.9998、CPU 全体 12%、GPU は使っていない）。**遅いのは私たちの地図の更新**。
  - 既定の LiDAR だけ（`--map fine`、1 か所 3 回）で、1 倍の地図の更新は中央値 0.071 秒・95% 値 0.087 秒・最大 0.128 秒。LiDAR の 1 周期（0.1 秒）の 71% を使い、
    1.4〜2.1% の更新が周期を超え、点群を 15〜27 回捨てた（`queue_drops`）。事前に決めた基準（捨てる回数 0、周期を超える割合 1% 以下）を満たさなかった。
  - 走行の結果はどれも完走だったが、実機でも地図の更新は実時間で追いつく必要がある。0.3 倍は計算の遅さを隠している。
  - 今は実機と同じセンサー（LiDAR＋深度カメラ 2 台、`PointCloudMapMulti`）を使うので、1 秒あたりの更新の回数が増え、1 倍はさらに厳しい。
- コードを見た限りの原因の見込み（`tapp/pointcloud_map_fine.py` の `update`）：
  1. 走査のたびに、**地図全体**で `TraversabilityMap(elev, raw_obstacle, ...)` を作り直している（傾き・勾配・粗さ・岩の膨らませ・`inflate_steep`）。変わったのは走査の周りだけ。
  2. 走査のたびに `elev`・`seen` の全体をコピーしている。
  3. 新しい障害物があるたびに、0.1m の細かい地図**全体**で `coarse_overlap` と `_inflated_coarse` を計算し直している。
  4. 0.5m のマスごとの Python のループ（`samples` の更新、中央値、`np.unique`）。
  まず**計測して、どこに時間がかかっているかを確かめてから**直すこと（見込みが外れていたら、それを報告する）。

## 作るもの
1. **計測**：保存済みの実際の点群、または実機と同じ点の数の偽の点群（LiDAR 約 2.9 万点、カメラ 1 台 214×125 点）で、`update` の各段の時間を測る。
   対象は `PointCloudMapFine`（`--ground-estimate all_returns` と `non_obstacle`）と `PointCloudMapMulti`（`lidar_real+depth2`）。
2. **速くする**（例。どれを使ってもよい）：
   - 変わったマスの周り（傾き・粗さ・膨らませの及ぶ範囲を含めた窓）だけを計算し直す。
   - 全体のコピーをやめる（窓だけを書き換える、または書き換え前後で入れ替える）。
   - `coarse_overlap`・`_inflated_coarse` を、新しい障害物の周りの窓だけで更新する。
   - マスごとのループを、まとめた配列の計算にする。
3. **目標**：研究 PC と同程度の CPU で、LiDAR 1 回の更新が 95% 値で **0.03 秒以下**、カメラ 1 台の 1 回が **0.01 秒以下**
   （1 倍で LiDAR 10Hz＋カメラ 2 台が、1 周期の半分以下に収まる目安）。届かなければ、どこまで届いたかと、残りの時間の内訳を報告する。

## 守ること
- **出力はバイト単位で変えない**。地図（`elev`・`seen`・`tm` の各配列・`lethal`・`fine_obstacle`・`fine_inflated`・`detected_obstacle`）が、
  同じ入力の列に対して、今の実装と**すべての更新のあとで**完全に一致すること。近似は入れない（窓の端の扱いも含めて一致させる）。
- 既存の結果・既存のテストは変えない。`ros2/` は変えない。結果を見て閾値を変えない。
- 036（`local`）の作業とは別。`obstacle_reference='local'` の経路には手を入れない（入口の分岐は残す）。
