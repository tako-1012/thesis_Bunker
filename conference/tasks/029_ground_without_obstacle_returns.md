## 背景（別の環境の会話は共有されないので、ここに書く）
- 023 の点群の地図（`tapp/pointcloud_map_fine.py`）は、0.5m のマスごとに「直近 64 点の高さの中央値」を地面の高さにしている。**障害物に当たった点もこの中に入る**。
- Gazebo の漂着物（箱）のマスでは、高さが箱の上面になり、本当の地面より **約 0.55m 高く**なる。傾斜は隣のマスとの高さの差から計算するので、
  **障害物の隣のマスが「急斜面」（25° 超）になる**。
- 研究 PC の `08OB87_-0706`（R1_05）で確かめた値：ロボットのマス (154,142) は高さが正しい（差 −0.01m）のに、隣の障害物のマス (154,143) が +0.56m 高いため、
  傾斜が **30.9°**（本当は 3.8°）になり、急斜面として通れないとされた。まわりの (152,143)・(153,142)・(155,143) なども 20〜39°（本当は 1〜5°）。
  ロボットがこの「偽の急斜面」に囲まれて、経路なしで止まった（028b の始点の解除は、急斜面を決して開けないので、この場合は開けられない）。
- 023 の調べでも、`08OB88_-1417` の誤って通れないとしたマス 197 のうち 102 が「点群の高さから計算した急斜面」だった。
- 障害物の点と地面の点を分けて地面の高さを推定するのは、点群の地図づくりの普通のやり方（地面の分離）。ここでは**今ある判定の値（古い地図より 0.3m 以上高い点）をそのまま使い**、新しい数値は作らない。

## 作るもの（**選んだときだけ**働く。既定のふるまい・既存の結果はバイト単位で変えない）
1. `PointCloudMapFine`（と、それを使う `PointCloudMapMulti`）に、地面の高さの推定のしかたを選ぶ引数を足す（例：`ground_estimate='all_returns'|'non_obstacle'`、既定は今までどおり `all_returns`）。
   新しいことは新しいファイルか、既定で今までと同じになる引数で足す（`pointcloud_map_fine.py` を直接変える場合も、既定の出力がバイト単位で同じであること）。
2. `non_obstacle` のとき：
   - 各マスの高さは、直近 64 点のうち**「古い地図の高さ（双線形補間）より 0.3m 以上高い点」を除いた点**の中央値にする（0.3m は障害物の判定と同じ値）。
   - そのマスの点がすべて除かれた（障害物の上面しか見えていない）ときは、高さは**古い地図の高さのまま**にする（その下の地面は見えていないため）。「見えた」の扱いは今までどおり。
   - 障害物の判定（0.1m の格子、0.3m・3 点、1 回の膨らませ）は変えない。傾斜・凸凹・コストの式も変えない（入力の高さだけが変わる）。
3. 実行の引数：`lidar_checks.py`・`lidar_planner.py` に `--ground-estimate all_returns|non_obstacle` を足し、manifest に記録する。既定は `all_returns`。
4. 限界を README に書く：古い地図から 0.3m 以上高くなった**本当の地形の変化**（新しくできた砂の盛り上がりなど）も、地面の高さには使われない（障害物として扱われる）。

## テスト `conference/tests/test_ground_estimate.py`（ROS2・Gazebo なしで動くこと）
1. 既定（`all_returns`）の出力が、今までとバイト単位で同じ。
2. 平らな地面に高さ 0.55m の箱を置いた偽の点群：`all_returns` では箱の隣のマスが急斜面になり（今の不具合の再現）、`non_obstacle` では隣のマスの傾斜が平らな地面と同じ程度（例：5° 未満）で、箱のマスは障害物のまま通れない。
3. 箱の上面しか見えないマスの高さは、古い地図の高さのまま。
4. 0.3m 未満のなだらかな地形の変化（古い地図と違う地面）は、`non_obstacle` でも高さに反映される。
5. `PointCloudMapMulti`（LiDAR＋カメラ）でも同じように働く。
6. 既存のテストがすべて通る。

## 変えないこと
- 既定のふるまい、既存の結果、障害物の判定の値（0.1m・0.3m・3 点・0.5m）、傾斜の上限（25°）、コストの式。
