## 背景
指示書019で、本物の砂浜（点群）6 か所を Gazebo で走らせると、`08OB88_-0167` で A\* も TA\*-S も BUNKER が**転倒**した（roll が最大 176°）。
Claude が記録を調べた結果（`results/gazebo_compare/physical_run/raw/08OB88_-0167_*`）：
- A\*：計画した経路が急斜面を 95 マス通っていた（比較用の A\* の仕様どおり）。
- TA\*-S：計画した経路は急斜面を 0 マスしか通らないが、走ると経路から 0.3〜0.8m ずれ、すぐ隣の 44〜46° の起伏に車体がかかり、
  その場での急旋回（角速度が上限の 1.0）のあとに後ろへ転倒した（t≈265s、x≈196m、y≈142m）。
- 一番考えられる原因：**急斜面の通れないマスは、ロボットの大きさの分だけ膨らませていない**（`TraversabilityMap` で膨らませているのは岩などの障害物だけ）。
  つまり、斜面についてはロボットを「点」として計画している。

## 1. 019 の転倒の判定（小さな直し）
- `experiments/gz_compare_report.py`：走行ごとに `rolled_over`（走行中のどこかで |roll| > 90°）を加える。状態は、転倒した走行を `stuck` ではなく
  `rollover` とする（元の記録の `status` は書き換えず、集計の列として加える）。転倒した時刻と位置（最初に |roll| > 90° になったサンプル）も出す。
- 表には、横傾き・縦傾きの 95% 値と並べて、**最大値と転倒の有無を必ず出す**（95% 値だけでは転倒が見えないため）。
- `results/gazebo_compare/REPORT_ja.md` の「停滞」の記述を、転倒であることが分かるように直す。元の記録・数値は変えない。集計を作り直したら、
  変わったファイルと理由を報告に書く。

## 2. 急斜面を、ロボットの大きさの分だけ膨らませる
- 新しいファイル `conference/tapp/footprint.py`：
  ```python
  def inflate_steep(tm, radius_m=None) -> np.ndarray   # 急斜面（tm.steep）を radius_m だけ膨らませ、tm.lethal と合わせた通れないマス
  def with_inflated_steep(sc, radius_m=None) -> dict    # シナリオの tmap の lethal だけを差し替えたもの（コストは同じ）
  ```
  - 膨らませる半径は、**岩と同じ `Robot().footprint_radius`（0.5m）を既定にする**（新しい値を作らない。調整しない）。
    比べるため 0.39m（車体の幅の半分、研究室の URDF と AgileX の仕様から）も走らせる。test の結果を見て選ばないこと。
  - 既存のファイル（`traversability.py` など）は変えない。既定のふるまいも変えない。
- スタートやゴールが膨らませた通れないマスに入る場合は、そのシナリオを「解けない」と記録する（地点をずらさない）。

## テスト：`conference/tests/test_footprint.py`
1. 平らな地形の中に急斜面のマスを 1 つ置くと、半径 0.5m の円の中が通れなくなり、外は通れる。コストは変わらない。
2. 膨らませない設定（半径 0）では、`tm.lethal` と同じになる。
3. `08OB88_-0167`（200m、漂着物なし）で、TA\*-S＋膨らませ（0.5m）の経路は、半径 0.5m 以内に急斜面がない（解けた場合）。
4. 転倒の判定：|roll| が 90° を超える偽の記録で `rolled_over` が真、超えない記録で偽になる。
5. 既存のテストがすべて通る。
